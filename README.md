# Avito ↔ Telegram bridge

Мост для одного продавца Авито и одного оператора в личном чате Telegram.
Поддерживаемый runtime: **Yandex Cloud Functions, Node.js 22 + YDB**.
Native Telegram и MAX в этом репозитории не реализованы.

Это реализация пилота с offline-проверками. Они не подтверждают облачную
приёмку, действующий webhook или реальную доставку. Бесплатность эксплуатации
и определённая задержка не гарантируются.

## Как проходит сообщение

```text
Avito / Telegram → проверка источника и владельца → YDB: dedup + outbox → HTTP 200
                                                     ↓
                                     приватный worker → API → статус доставки
```

Ingress `index.handler` не отправляет сообщения. Ошибка сохранения возвращает 503.
Worker `worker.handler` выполняет POST после фиксации `sending` в БД. Результат —
`sent`, `rejected` или `unknown`. Таймаут и авария после POST не запускают повторную
отправку автоматически. Это не exactly-once доставка.

- Telegram проверяется через `secret_token`, затем ID владельца и тип `private`.
- Ответ покупателю разрешён только через Reply на карточку своего `TELEGRAM_BOT_ID`.
  Завершающий маркер задаёт диалог; last-chat fallback отсутствует.
- Avito проверяется отдельной capability в `avito_secret` HTTPS URL. Поддерживается
  также `x-avito-webhook-secret`, если заголовок добавляет доверенный шлюз. Это
  наш механизм доступа, не заявление о штатной подписи webhook со стороны Авито.
  Секрет и query URL нельзя сохранять в access logs.
- `AUTO_REPLY_ENABLED=true` включает автоответ на каждое новое входящее сообщение,
  а не один раз на диалог. По умолчанию он выключен. Собственные события продавца
  игнорируются, повторные события отсекаются durable dedup в пределах 7 суток.
- **`DELIVERY_ENABLED=true` требуется отдельно в окружении worker.** По умолчанию
  worker ничего не отправляет и не меняет очередь. Включение разрешит отправку
  накопленных `pending`: сначала проверить backlog в рамках процедуры выпуска.
- Поддерживается текст ответа оператора до 4000 символов. Входящие нетекстовые
  сообщения дают уведомление со ссылкой; пересылки файлов нет. Длинная карточка
  сокращается с пометкой, полный текст доступен на Авито.

## Локальная проверка

```sh
# Node.js из .nvmrc (22.23.2)
npm ci --ignore-scripts --no-audit --no-fund
npm test
npm run simulate
npm run emulator
./ops/run
```

`npm test`, `simulate` и `emulator` не используют клиентские credentials и не
отправляют сообщения. `simulate` запускает один offline-сценарий; `emulator`
принимает по одному фиктивному Avito JSON в строке. Память эмулятора заменяет БД
только для демонстрации. Тесты проверяют контракты адаптеров с mock HTTP,
авторизацию, dedup, конкуренцию claim и неопределённый результат отправки;
настоящие транзакции YDB ими не проверяются.

В `.github/workflows/check.yml` настроен CI для push и pull request: Node 22, установка по lockfile без
install scripts, тесты и offline smoke. Actions закреплены SHA, права только на
чтение, credentials выпуска не передаются. Результат запуска проверяется отдельно
в GitHub Actions. Облачный выпуск выполняется через Ansible, в CI его нет.

`ping` — отдельный сетевой GET health на явно заданный HTTPS URL. `register:tg` и
`register:avito` меняют webhook и требуют отдельного согласованного запуска.
Скрипты не ищут функцию через default-профиль `yc`.

- [Статус native Telegram](examples/telegram-serverless/README.md): что нужно проверить для отдельного переноса.

Один клиент получает собственные БД, SA, функции, токены и получателя. Обязательного
Lockbox нет: значения секретов передаются через настройки платформы; конфигурация
`secretEnvironment` хранит только имена локальных `DEPLOY_*`.

Пилот ограничен 100 событиями с заданиями и 2000 dedup ID на одну запись, 10 новыми
событиями за 10 секунд на запись и размером документа. Это особенно важно для
общей записи оператора: после 100 ответов в пределах retention приём новых ответов
будет отклонён до освобождения истории. Перед длительной эксплуатацией нужно
изменить модель хранения или согласовать меньший срок истории; не удалять задания
для обхода ограничения. Подробности — в архитектуре и runbook.
