# Avito ↔ Telegram: инструкции агенту

Прочитать [README](README.md), для операций — [RUNBOOK](RUNBOOK.md).
Этот файл и локальные документы обязательны в самостоятельной передаче проекта.
В workspace общий контекст — `../AGENTS.md` и `../ARCHITECTURE.md`.

## Карта кода

- YCF Node.js 22 + YDB: webhook `index.handler`, приватная доставка `worker.handler`.
  `lib/avito.js` и `lib/telegram.js` — внешние адаптеры; `lib/records.js`,
  `lib/ydb-store.js`, `lib/delivery-worker.js` — сохранение и доставка.
- `ops/runtime.json` закрепляет поддерживаемый provider и обязательные ID/секреты.
  `vendor-core/` хранит исходник и manifest, `lib/core.js` — скомпилированное ядро.

## Инварианты

- Ответ продавца разрешён только из личного чата проверенного `TELEGRAM_CHAT_ID`
  через Reply на карточку своего `TELEGRAM_BOT_ID`. Адрес Avito берётся из проверенного
  завершающего маркера карточки. Текст покупателя не может подменять маршрут.
- Не восстанавливать `ACTIVE_AVITO_CHAT_ID`, last-chat в памяти или fallback-адресата.
  Проверять `AVITO_USER_ID`, токен и принадлежность конфигурации одному клиенту.
- `AUTO_REPLY_ENABLED` остаётся opt-in. Успех отправки подтверждать реальным результатом,
  отдельные задачи для разных адресатов; `unknown` не повторять автоматически.
- Worker отправляет только при `DELIVERY_ENABLED=true`; включение открывает весь
  backlog pending и требует отдельной проверки. Выключение не отменяет уже начатый POST.
- Native Telegram и MAX здесь не реализованы. Не возвращать устаревший пример SDK
  или config другого provider без отдельной реализации и staging-приёмки.
- Telegram webhook проверяет secret_token. Capability Avito в `avito_secret` — секрет:
  не печатать полный URL/query в логах, командах отчёта и документах с рабочими значениями.
- Сначала сохранять событие/intent/outbox, затем ACK; внешние POST вне транзакции.
  Worker не делать публичным.

## Проверки и операции

Node.js 22: `npm ci --ignore-scripts`, `npm test`, `npm run emulator`.
Emulator offline. `npm run ping`, `register:tg`, `register:avito` — сетевые операции,
регистрация меняет webhook; не запускать их как обычные тесты. Остальные вспомогательные
скрипты проверять перед запуском на сетевые эффекты.
Ядро менять исходником/сборкой/лицензией/manifest вместе; `npm run verify:core` — хеши.
Для документации достаточно diff и ссылок; `./ops/run` — offline status.

Сохранить чужой Git-diff, не хранить токены, личные сообщения и сырые события в Git
или логах. Разработка не означает commit/push/deploy. Выпуск и реальные отправки
выполнять в разрешённом объёме по runbook; регистрацию webhook учитывать отдельно.
После timeout сначала сверить receipt и фактическую доставку/версию, не повторять POST
вслепую. В результате отделять моки от подтверждённого end-to-end сценария staging.

## Секреты

Секреты передаются через защищённые настройки платформы; обязательного Lockbox нет
ни в staging, ни в production. YCF: `ops/config.example.json` содержит только имена
`secretEnvironment` → локальные `DEPLOY_*`, значения читаются при preflight/deploy/verify.
Доступ к облаку/app и IAM — ответственность заказчика; защита сборки/кода и отсутствие
секретов в Git, логах и артефактах — студии. Подробности и ротация — в RUNBOOK.
