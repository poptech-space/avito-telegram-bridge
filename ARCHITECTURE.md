# Архитектура Avito ↔ Telegram

## Поддерживаемая граница

Один клиент, один продавец Авито, один Telegram-бот и один оператор в личном чате.
YCF Node.js 22 + изолированная YDB клиента. `ops/runtime.json` разрешает только YCF.
Примеры других проектов не добавляют поддержку native Telegram или MAX этому мосту.

## Компоненты

| Компонент | Назначение |
|---|---|
| `index.js` | GET health; проверка POST, источника, actor, ID и формы события; сохранение intent |
| `lib/webhook-security.js` | Сравнение секретов по байтам, заголовки, ограничение тела 64 KiB |
| `lib/core.js` + `vendor-core/` | Версионированное ядро dedup, лимитов и состояний доставки |
| `lib/records.js`, `lib/ydb-store.js` | HMAC-ключи, serializable read/write, атомарная запись документа и индекса очереди |
| `worker.js`, `lib/scan-worker.js` | Явное разрешение доставки, приватный timer ingress, lease и ограниченный проход |
| `lib/delivery-worker.js` | Claim → POST вне транзакции → результат; просроченная sending становится unknown |
| `lib/avito.js`, `lib/telegram.js` | HTTP с дедлайнами, проверка ответов, отсутствие provider body в ошибках |
| `ops/` | Ansible localhost, изолированная сборка чистого SHA, manifest, отдельные операции выпуска |

Документ хранится по HMAC от `avito:<chat_id>` или `tg:<owner_id>`. Dedup, событие
и задания фиксируются вместе с `bot_queue`. При ошибке коммита ACK не возвращается.
Память процесса используется для драйвера и OAuth-кеша, не для маршрута или dedup.
OAuth-кеш учитывает credentials и срок `expires_in`; холодный старт потребует авторизации заново.

## Доставка и остановка

Без `DELIVERY_ENABLED=true` worker не обращается к очереди. Это защита от случайного
дренирования после выпуска, не отмена ранее запущенного POST. Остановка уже работающего
worker требует отдельной операционной процедуры. Включение переключателя отправит
оставшиеся pending; сначала проверить их возраст и адресатов.

Worker имеет общий lease на 60 секунд и ограничение до 10 записей за вызов,
до 2 заданий за проход записи. Между claim проверяется бюджет времени. Каждый
HTTP-вызов ограничен 5 секундами, однако сеть, OAuth и БД могут исчерпать timeout
функции: это не гарантия времени завершения. Claim перед POST исключает повторный
POST конкурирующим drain. Авария между claim и результатом оставляет sending,
которая после 60 секунд переводится в unknown.

Только подтверждённый ответ с ID сообщения считается sent. Явный 4xx считается
rejected. Сетевой сбой, 5xx и некорректное подтверждение — unknown. Ни rejected,
ни unknown не повторяются таймером. Повтор rejected разрешён только адресной командой
оператора. Без idempotency key провайдера exactly-once отправка не гарантируется.

Период таймера входит в задержку доставки. При интервале 60 секунд ожидание worker
может добавить почти минуту ещё до HTTP отправки. Нельзя обещать отклик за секунду
по времени выполнения ingress. Пустые вызовы таймера тоже расходуют ресурсы.

## Безопасность

Источник подтверждается до разбора бизнес-события. ID в JSON не доказывает источник.
Отдельно проверяются private-чат владельца и собственный бот в Reply. Маркер маршрута
привязан к концу карточки, поэтому текст покупателя с похожим маркером не меняет адресата.
Worker разрешает Telegram-доставку только настроенному оператору; рассылки по базе нет.
Адрес Avito берётся из сохранённого задания, сформированного проверенным ingress.

Capability URL Авито — bearer-секрет, не криптографическая подпись тела. Подмена
невозможна только пока секрет не раскрыт. Gateway/access logs, history команд и
системы аналитики не должны сохранять query. Runtime SA ограничивается БД клиента;
worker закрыт IAM, а проверка HTTP-события является дополнительной защитой.

## Известные ограничения

- Одна запись на Avito-диалог, одна общая запись на Telegram-оператора.
- До 100 submissions за 90 суток, 2000 dedup ID за 7 суток, документ до 150000
  символов, до 10 новых событий за 10 секунд на запись. Dedup после 7 суток не обещается.
- После достижения лимита возвращается 503 до освобождения истории. Лимит 100
  ответов оператора делает текущую модель пилотной; для постоянной эксплуатации
  нужны отдельные записи событий/заданий и индекс dedup. Не очищать pending/unknown
  автоматически ради места.
- Lease ограничивает параллельность, но не реализует общий rate limiter API или DLQ.
- Отдельный scheduler обязателен для фоновой доставки; автоматически не создаётся.
- Тесты с memory-store не подтверждают транзакции YDB, IAM, TTL, сеть и реальные квоты.
- Вложения, управление несколькими продавцами, групповой чат и массовая рассылка отсутствуют.

Решение и последствия: [ADR](docs/adr/0001-controlled-delivery.md).
